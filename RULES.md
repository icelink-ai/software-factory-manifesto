# Rules

Every rule in the manifesto, by id. Generated by `scripts/check.py --write`; do not edit.
Each id links to the page that explains it. MUST, SHOULD and MAY follow RFC 2119.


## 01. Work intake

- [IN-01](docs/01-work-intake/README.md) Work MUST enter through the tools the team already uses (chat, issue tracker, alerts), and every request MUST become a tracked item with a link back to where it came from.
- [IN-02](docs/01-work-intake/README.md) Every request MUST pass a triage step before any builder runs. Triage MUST be read-only.
- [IN-03](docs/01-work-intake/README.md) Triage MUST output structured data (risk, kind, size, acceptance criteria, questions), and a deterministic script, not the triage agent, MUST apply it.
- [IN-04](docs/01-work-intake/README.md) A request with missing information MUST go back to the requester as questions, not forward to a builder with guesses.
- [IN-05](docs/01-work-intake/README.md) The factory MUST only pick up work that was explicitly opted in (a label, a command, a channel).
- [IN-06](docs/01-work-intake/README.md) A request too large for one bounded run MUST be split into an ordered stack of small parts.
- [IN-07](docs/01-work-intake/intake-surfaces.md) Each surface (chat, issue tracker, alerting) MUST create the same kind of tracked item, so everything after intake is surface-agnostic.
- [IN-08](docs/01-work-intake/intake-surfaces.md) The tracked item MUST carry a machine-readable link to its origin (for example a hidden marker with channel and thread id), and the factory MUST post status back to that origin.
- [IN-09](docs/01-work-intake/intake-surfaces.md) Intake MUST verify the authenticity of every inbound event (request signatures, webhook secrets) before creating anything.
- [IN-10](docs/01-work-intake/intake-surfaces.md) Intake MUST NOT classify, plan or build. It records and routes.
- [IN-11](docs/01-work-intake/intake-surfaces.md) Replies from the requester on the origin thread SHOULD flow back into the tracked item automatically, so answering a question needs no context switch.
- [IN-12](docs/01-work-intake/intake-surfaces.md) The source of a request (chat, alert, customer feedback) MUST be recorded separately from its kind. Source says where it came from; kind says what it is.
- [IN-13](docs/01-work-intake/triage-and-risk.md) The triage agent MUST have read access only: repository, product spec, memory. It MUST NOT push, label or comment.
- [IN-14](docs/01-work-intake/triage-and-risk.md) Triage MUST return a schema-validated object with at least: `risk`, `kind`, `size`, `goal`, `acceptance_criteria`, `out_of_scope`, `plan`, `affected_paths`, `questions`.
- [IN-15](docs/01-work-intake/triage-and-risk.md) A script MUST apply the object: rewrite the item's criteria and plan, set the risk and kind labels, and either queue the build or post the questions.
- [IN-16](docs/01-work-intake/triage-and-risk.md) Triage SHOULD use a strong model. Cheap models are acceptable only for narrow classification with its own eval.
- [IN-17](docs/01-work-intake/triage-and-risk.md) Risk MUST be assigned from what a wrong change could break, not from how hard the change looks.
- [IN-18](docs/01-work-intake/triage-and-risk.md) An item with no risk label MUST be treated as `high`.
- [IN-19](docs/01-work-intake/request-kinds.md) Triage MUST assign exactly one kind: `bug`, `feature`, `incident`, `docs`, `refactor` or `chore`.
- [IN-20](docs/01-work-intake/request-kinds.md) When unsure between two kinds, triage MUST pick the more restrictive one. A bug fix that needs new behavior is a `feature`.
- [IN-21](docs/01-work-intake/request-kinds.md) An item with no kind MUST be treated as `feature`.
- [IN-22](docs/01-work-intake/request-kinds.md) Kind MUST NOT add states to the job state machine. It parameterizes the existing stages.
- [IN-23](docs/01-work-intake/request-kinds.md) The effective merge ceiling MUST be the most restrictive of risk, kind and protected paths (see [Risk × kind](../06-merge-policy/risk-times-kind.md)).
- [IN-24](docs/01-work-intake/request-kinds.md) A `bug` or `incident` that the builder cannot reproduce MUST stop with no PR and go to `hold` with a "not reproduced" note.
- [IN-25](docs/01-work-intake/sizing-and-stacks.md) A job MUST fit one bounded run (a fixed budget of turns and wall-clock time) and touch one module.
- [IN-26](docs/01-work-intake/sizing-and-stacks.md) Triage MUST assign a size (`S`, `M`, `L`). Size `L` MUST NOT go to a builder.
- [IN-27](docs/01-work-intake/sizing-and-stacks.md) An `L` request MUST be split into 2 to 5 ordered parts, each a job with its own risk and kind, linked to a parent item.
- [IN-28](docs/01-work-intake/sizing-and-stacks.md) Only the first part MAY start. Each next part MUST start only after the previous one merges, so it builds on merged code, not on an open branch.
- [IN-29](docs/01-work-intake/sizing-and-stacks.md) The stack MUST stop when any part fails or is put on hold, and the requester MUST be told which part stopped and why.
- [IN-30](docs/01-work-intake/sizing-and-stacks.md) Re-running triage on a parent that is already a stack MUST NOT create parts again.

## 02. Deterministic spine

- [SP-01](docs/02-deterministic-spine/README.md) The sequence of stages and the transitions between them MUST be implemented in deterministic code, not decided by an LLM.
- [SP-02](docs/02-deterministic-spine/README.md) Each job MUST have an explicit state from a closed set, and only transitions from a declared table MUST be allowed.
- [SP-03](docs/02-deterministic-spine/README.md) Job state MUST have exactly one writer: a CLI or service that enforces the table. Agents call it; they never write the state store.
- [SP-04](docs/02-deterministic-spine/README.md) Every stage MUST be idempotent on the identity of the event that triggered it.
- [SP-05](docs/02-deterministic-spine/README.md) Every failure MUST land the job in a visible state and notify the requester's thread. No job may disappear silently.
- [SP-06](docs/02-deterministic-spine/README.md) Every agent invocation MUST have hard limits: turns, wall-clock time and concurrency.
- [SP-07](docs/02-deterministic-spine/README.md) Any state other than the final one MUST be able to move to `hold`, so a person can stop anything at any time.
- [SP-08](docs/02-deterministic-spine/job-state-machine.md) The job MUST be in exactly one of these states: `triage`, `needs_info`, `building`, `reviewing`, `changes_requested`, `awaiting_human`, `merged`, `failed`, `hold`.
- [SP-09](docs/02-deterministic-spine/job-state-machine.md) Only the transitions in the table below MUST be accepted. An invalid transition MUST be rejected with an error and MUST NOT modify the record.
- [SP-10](docs/02-deterministic-spine/job-state-machine.md) Every transition MUST append to the job's history: target state, UTC timestamp, a short note saying who or what moved it.
- [SP-11](docs/02-deterministic-spine/job-state-machine.md) Entering `building` MUST increment the attempt counter.
- [SP-12](docs/02-deterministic-spine/job-state-machine.md) `merged` is final. Reopened work is a new job.
- [SP-13](docs/02-deterministic-spine/job-state-machine.md) New work types, sources or policies SHOULD be parameters (labels, fields) on existing states, not new states.
- [SP-14](docs/02-deterministic-spine/single-writer.md) Exactly one program (the job CLI) MUST write job records. Its transition table is the source of truth; documentation mirrors it.
- [SP-15](docs/02-deterministic-spine/single-writer.md) Agents MUST NOT have write credentials for the job store. They MAY call commands that the spine exposes.
- [SP-16](docs/02-deterministic-spine/single-writer.md) Workflow steps MUST call the CLI through a wrapper that turns network or credential errors into warnings, so a registry outage never fails a build.
- [SP-17](docs/02-deterministic-spine/single-writer.md) Read-only consumers (status commands, dashboards, stuck-job alerts) MAY read the store directly and MUST NOT write it.
- [SP-18](docs/02-deterministic-spine/single-writer.md) The CLI MUST be testable with an in-memory store, and its tests MUST cover every valid and invalid transition.
- [SP-19](docs/02-deterministic-spine/idempotent-dispatch.md) Every dispatch MUST record the delivery id of the triggering event before starting work, using a create-if-absent write. A second delivery with the same id MUST be a no-op.
- [SP-20](docs/02-deterministic-spine/idempotent-dispatch.md) Every dispatch MUST also be keyed on (repository, item, stage). A new run for the same key MUST be refused while the previous one could still be running (for example within the run's wall-clock limit).
- [SP-21](docs/02-deterministic-spine/idempotent-dispatch.md) When dispatch itself fails (the runner could not start), the receiver MUST return an error so the sender retries, instead of acknowledging and dropping the event.
- [SP-22](docs/02-deterministic-spine/idempotent-dispatch.md) Each trigger (label, command, event) MUST dispatch only its own stage.
- [SP-23](docs/02-deterministic-spine/idempotent-dispatch.md) When moving a stage from one execution engine to another, the old path MUST be disabled by configuration in the same change, so both never run.
- [SP-24](docs/02-deterministic-spine/failure-handling.md) Every workflow MUST end with a failure hook that moves the job to `failed` (when the current state allows it) and posts to the origin thread and an operations channel, with the stage that failed and a link to the log.
- [SP-25](docs/02-deterministic-spine/failure-handling.md) The failure hook itself MUST never fail the workflow: errors in it become warnings.
- [SP-26](docs/02-deterministic-spine/failure-handling.md) Retries MUST be bounded: attempts per job, review rounds per PR, re-triage per request. When the bound is reached, the job MUST go to `hold`.
- [SP-27](docs/02-deterministic-spine/failure-handling.md) A scheduled job SHOULD alert on jobs that stayed in the same active state longer than a threshold. `needs_info`, `hold` and `merged` are excluded; `failed` is included.
- [SP-28](docs/02-deterministic-spine/failure-handling.md) A person MUST be able to recover any job with one action: move it from `hold` or `failed` back to `triage` or `building`.

## 03. Guardrails

- [GR-01](docs/03-guardrails/README.md) Investment in guardrails MUST follow the inverted pyramid: code structure first, then static analysis, then runtime and formal checks, then a small amount of prose, then human review.
- [GR-02](docs/03-guardrails/README.md) A correction made to agent output more than once MUST become an automated check (lint rule, type, test, dependency rule) whose error message explains the fix.
- [GR-03](docs/03-guardrails/README.md) Agent instruction files MUST contain only what an agent cannot discover from the code.
- [GR-04](docs/03-guardrails/README.md) Actions that cannot be undone MUST be blocked by deny rules enforced by the harness, not discouraged by the prompt.
- [GR-05](docs/03-guardrails/README.md) Changes to protected paths (CI, the factory definition, infrastructure, auth) MUST always need a human merge.
- [GR-06](docs/03-guardrails/README.md) Each agent MUST get only the tools and credentials its stage needs.
- [GR-07](docs/03-guardrails/inverted-pyramid.md) The first response to a recurring agent mistake MUST be to ask "can the code make this impossible?" (a narrower API, a module boundary, a type).
- [GR-08](docs/03-guardrails/inverted-pyramid.md) If not, the next response MUST be a static check (lint, types, dependency analyzer).
- [GR-09](docs/03-guardrails/inverted-pyramid.md) Runtime and formal verification SHOULD cover flows where static checks cannot reach: UI behavior, concurrency, money.
- [GR-10](docs/03-guardrails/inverted-pyramid.md) A prose rule (instructions file, skill) is acceptable only when the above are not feasible, and it SHOULD be revisited when tooling improves.
- [GR-11](docs/03-guardrails/inverted-pyramid.md) Human review MUST be reserved for judgment: product fit, risk acceptance, taste.
- [GR-12](docs/03-guardrails/teaching-lint-rules.md) When a reviewer (human or agent) corrects the same pattern twice, a `refactor` job MUST be opened to encode it as a check.
- [GR-13](docs/03-guardrails/teaching-lint-rules.md) The error message of a custom rule MUST say what to do instead and why, in one or two sentences, so the agent fixes the cause rather than silencing the rule.
- [GR-14](docs/03-guardrails/teaching-lint-rules.md) Suppression comments for custom rules SHOULD be disallowed or require a linked reason.
- [GR-15](docs/03-guardrails/teaching-lint-rules.md) New rules MUST run in the single gate, so they apply to builders, CI and humans alike.
- [GR-16](docs/03-guardrails/teaching-lint-rules.md) The count of checks created from corrections SHOULD be tracked as a metric of how well the team "tends the garden".
- [GR-17](docs/03-guardrails/minimal-agent-instructions.md) The repository instructions file (`AGENTS.md`, `CLAUDE.md` or equivalent) MUST contain only information an agent cannot discover by reading the code: where the spec lives, what is forbidden and why, how to run the gate, how to finish a task.
- [GR-18](docs/03-guardrails/minimal-agent-instructions.md) It MUST NOT use emphatic markers ("IMPORTANT!", all caps, repeated "NEVER") as a substitute for enforcement. Current models perform worse with them.
- [GR-19](docs/03-guardrails/minimal-agent-instructions.md) Every rule in the file that can be enforced by a check SHOULD be moved into the gate, and removed from the file.
- [GR-20](docs/03-guardrails/minimal-agent-instructions.md) The file MUST be reviewed periodically, and stale or conflicting instructions removed.
- [GR-21](docs/03-guardrails/minimal-agent-instructions.md) A "Never" list SHOULD exist and SHOULD match the deny rules enforced by the harness, so the prose explains what the harness enforces.
- [GR-22](docs/03-guardrails/deny-rules-and-protected-paths.md) Irreversible actions MUST be denied by the harness before any classifier or model judgment runs. Minimum list: reading secret files (`.env*`, keys, state files), force push, rewriting the main branch, deleting branches or data, deploying or applying infrastructure, merging one's own PR.
- [GR-23](docs/03-guardrails/deny-rules-and-protected-paths.md) Deny rules MUST be versioned in the repository and reviewed like code.
- [GR-24](docs/03-guardrails/deny-rules-and-protected-paths.md) The merge policy MUST define protected paths, and any PR touching them MUST need a human merge regardless of risk or kind.
- [GR-25](docs/03-guardrails/deny-rules-and-protected-paths.md) Protected paths MUST include at least: CI and workflow definitions, the factory's own definition (prompts, gate, policy), agent instruction files, infrastructure, auth and permission code.
- [GR-26](docs/03-guardrails/deny-rules-and-protected-paths.md) The factory's credentials SHOULD NOT allow changing CI definitions at all. When a job needs such a change, the builder MUST leave the patch for a person to apply.
- [GR-27](docs/03-guardrails/least-privilege-agents.md) Each stage (triage, build, review, edge functions) MUST run under its own identity with its own permission set.
- [GR-28](docs/03-guardrails/least-privilege-agents.md) Identity MUST come from authentication (the service account or token of the caller), never from a parameter the agent passes.
- [GR-29](docs/03-guardrails/least-privilege-agents.md) Triage and review MUST be read-only on the repository. Only the builder MAY push, and only to its own branch.
- [GR-30](docs/03-guardrails/least-privilege-agents.md) Edge functions (feedback triage, alert triage, data questions) SHOULD be small domain agents with one or two tools and their own eval, not the general coding agent.
- [GR-31](docs/03-guardrails/least-privilege-agents.md) Access SHOULD grow with demonstrated reliability, like a new employee's: read-only first, then scoped actions, then ownership of an outcome.

## 04. Sandboxes

- [SB-01](docs/04-sandboxes/README.md) Builder runs MUST execute in an isolated, disposable environment created for that run and destroyed after it.
- [SB-02](docs/04-sandboxes/README.md) The environment MUST be able to run the whole system under test locally, with mocks for every third-party and production service.
- [SB-03](docs/04-sandboxes/README.md) No agent MAY touch production services to test its work.
- [SB-04](docs/04-sandboxes/README.md) Secrets MUST NOT be readable by the model. Network egress MUST be restricted to an allowlist by default.
- [SB-05](docs/04-sandboxes/README.md) Sandbox limits MUST be enforced at the operating system level (files, folders, hosts, child processes), not only by tool permissions.
- [SB-06](docs/04-sandboxes/README.md) What leaves the sandbox (commits, pushes, messages, comments) MUST still pass deny rules and the merge policy.
- [SB-07](docs/04-sandboxes/disposable-environments.md) Run environments MUST be created from a versioned image plus a setup script kept in the repository.
- [SB-08](docs/04-sandboxes/disposable-environments.md) The image or snapshot SHOULD be rebuilt on a schedule from the latest main branch, so runs start with warm dependencies and current code.
- [SB-09](docs/04-sandboxes/disposable-environments.md) When the image build breaks, the factory SHOULD open a job to fix it, so an agent is the first responder.
- [SB-10](docs/04-sandboxes/disposable-environments.md) Every run MUST have a wall-clock limit and MUST be destroyed at the end, including on failure.
- [SB-11](docs/04-sandboxes/disposable-environments.md) Nothing a run produces MAY persist except what it explicitly publishes (branch, PR, artifacts, memory entries).
- [SB-12](docs/04-sandboxes/local-with-mocks.md) Every service the factory works on MUST start locally with one command (for example a compose file).
- [SB-13](docs/04-sandboxes/local-with-mocks.md) Every third-party dependency (payments, email, auth providers, external APIs) MUST have a mock that runs in the same environment.
- [SB-14](docs/04-sandboxes/local-with-mocks.md) Databases MUST start from seeds or fixtures kept in the repository.
- [SB-15](docs/04-sandboxes/local-with-mocks.md) Shared staging environments SHOULD NOT be used for agent verification; they create contention and leak state between runs.
- [SB-16](docs/04-sandboxes/local-with-mocks.md) A service that cannot run locally MUST be listed as a gap, with the work needed to close it, before the factory is allowed to build features on it.
- [SB-17](docs/04-sandboxes/secrets-and-network.md) Credentials MUST be injected outside the model's context (network-level injection, short-lived tokens in the tool layer), never as files or environment variables the agent can print.
- [SB-18](docs/04-sandboxes/secrets-and-network.md) Tokens MUST be short-lived and scoped to one repository and the minimum permissions.
- [SB-19](docs/04-sandboxes/secrets-and-network.md) Cloud access from runs MUST use workload identity federation or equivalent. Long-lived key files MUST NOT exist.
- [SB-20](docs/04-sandboxes/secrets-and-network.md) Network egress MUST be deny-by-default, with an allowlist (package registries, the code host, the memory server).
- [SB-21](docs/04-sandboxes/secrets-and-network.md) If an agent finds a secret in the repository or in output, it MUST stop and report it, not use it.
- [SB-22](docs/04-sandboxes/parallel-work-isolation.md) Each job MUST work on its own branch, named after the job (for example `factory/issue-<n>`).
- [SB-23](docs/04-sandboxes/parallel-work-isolation.md) In the cloud, each job MUST get its own environment, which makes this automatic.
- [SB-24](docs/04-sandboxes/parallel-work-isolation.md) When agents run locally in a shared clone, each MUST use its own git worktree created from an up-to-date main, and MUST NOT switch branches in the shared checkout.
- [SB-25](docs/04-sandboxes/parallel-work-isolation.md) A worktree MUST be removed after its branch is pushed.
- [SB-26](docs/04-sandboxes/parallel-work-isolation.md) A concurrency limit MUST cap how many jobs run at once.

## 05. Verification

- [VE-01](docs/05-verification/README.md) One deterministic gate script MUST pass before a PR exists. Hooks, CI and the factory MUST run the same script.
- [VE-02](docs/05-verification/README.md) The builder MUST attach evidence to every PR, of the type its request kind requires.
- [VE-03](docs/05-verification/README.md) Every PR MUST be reviewed by an agent that did not write it, in a clean context, before any merge decision.
- [VE-04](docs/05-verification/README.md) The reviewer MUST check the PR against the acceptance criteria from triage and the product spec, not only against the diff.
- [VE-05](docs/05-verification/README.md) Review returns to the builder MUST be bounded (for example two rounds), after which the job goes to `hold`.
- [VE-06](docs/05-verification/README.md) Agents SHOULD be able to drive the running application (browser automation, CLI, traces), because that is what lets them check their own work.
- [VE-07](docs/05-verification/single-gate.md) The repository MUST have exactly one gate script, and it MUST be the only definition of "passes": lint, format, type check, tests, build, repository guardrails (for example "no app imports another app"), infrastructure validation.
- [VE-08](docs/05-verification/single-gate.md) CI MUST run exactly that script, not a parallel list of steps.
- [VE-09](docs/05-verification/single-gate.md) The factory MUST NOT open a PR while the gate fails. It comments on the tracked item with the log link instead.
- [VE-10](docs/05-verification/single-gate.md) The gate SHOULD offer a fast mode (lint and format only) for inner-loop hooks.
- [VE-11](docs/05-verification/single-gate.md) An agent that needs to work around a rule MUST NOT disable it. It MUST explain the conflict in the PR.
- [VE-12](docs/05-verification/single-gate.md) Flaky tests MUST be fixed or quarantined by a person-owned job; agents MUST NOT retry the gate until it passes by chance.
- [VE-13](docs/05-verification/evidence-artifacts.md) The PR description MUST contain a verification section with the evidence, or links to it, organized by acceptance criterion.
- [VE-14](docs/05-verification/evidence-artifacts.md) For a bug or incident, the evidence MUST include a test that fails on the base branch and passes on the PR branch, with both outputs.
- [VE-15](docs/05-verification/evidence-artifacts.md) For a user-visible change, the evidence SHOULD include a screenshot or short video of the running application, produced by the agent driving it.
- [VE-16](docs/05-verification/evidence-artifacts.md) Evidence MUST be produced by running the software in the sandbox, not described.
- [VE-17](docs/05-verification/evidence-artifacts.md) A feature map (the list of user-facing features and how to reach them) and test CLIs SHOULD exist so agents share a vocabulary and spend fewer tokens driving the app.
- [VE-18](docs/05-verification/evidence-artifacts.md) The share of PRs with evidence SHOULD be tracked.
- [VE-19](docs/05-verification/hooks.md) The agent harness SHOULD run the fast gate (lint, format) after each edit.
- [VE-20](docs/05-verification/hooks.md) It SHOULD run the tests for the affected area when the agent marks a task done, and the full gate when the session ends.
- [VE-21](docs/05-verification/hooks.md) A hook that finds a problem MUST exit with the code the harness interprets as "send the agent back" (in some harnesses that is exit code 2; other non-zero codes may be treated as informational). Check your harness documentation; a wrong exit code silently disables the hook.
- [VE-22](docs/05-verification/hooks.md) Hooks MUST call the same gate script, in fast or full mode, not a separate set of commands.
- [VE-23](docs/05-verification/independent-reviewer.md) The reviewer MUST run in a fresh session that has not seen the builder's reasoning.
- [VE-24](docs/05-verification/independent-reviewer.md) The reviewer's model MUST be at least as capable as the builder's. A weaker reviewer nitpicks valid code, misreads intent and creates costly rework loops.
- [VE-25](docs/05-verification/independent-reviewer.md) The reviewer's inputs MUST be: the diff, the evidence, the acceptance criteria and out of scope from triage, the relevant product spec, and the kind's evidence requirements.
- [VE-26](docs/05-verification/independent-reviewer.md) The reviewer MUST return a structured verdict (approve or changes) with findings that each cite a file and line, and a deterministic script MUST apply it as labels and one comment.
- [VE-27](docs/05-verification/independent-reviewer.md) One reviewer fed with product requirements SHOULD be preferred over several adversarial models arguing. Multi-model debate consumes huge token budgets and drifts from product intent.
- [VE-28](docs/05-verification/independent-reviewer.md) The reviewer MUST NOT push code. It requests changes; the builder makes them.
- [VE-29](docs/05-verification/return-loop.md) When the reviewer requests changes, the spine MUST send the PR back to the builder with the review findings as work material.
- [VE-30](docs/05-verification/return-loop.md) The number of returns MUST be counted in a durable place attached to the PR (for example hidden markers in comments), not in the agent's memory.
- [VE-31](docs/05-verification/return-loop.md) After a fixed number of returns (we use two), the next request for changes MUST put the job on `hold`, comment the reason on the PR and notify the origin thread.
- [VE-32](docs/05-verification/return-loop.md) On each return, the builder MUST address the findings or reply why a finding is wrong. It MUST NOT silently ignore one.

## 06. Merge policy

- [MG-01](docs/06-merge-policy/README.md) A deterministic script MUST make every merge decision from the PR's labels, paths, CI status and review verdict. No agent decides to merge.
- [MG-02](docs/06-merge-policy/README.md) Auto-merge MUST require all of: factory-made PR, risk in the auto-merge list, kind that allows it, reviewer approval, no protected path, no `hold`, CI green on the latest commit.
- [MG-03](docs/06-merge-policy/README.md) Human approvals MUST scale with risk (for example low 0, medium 1, high 2), and the kind's minimum MUST apply when it is higher.
- [MG-04](docs/06-merge-policy/README.md) A PR without a risk label MUST be treated as high risk.
- [MG-05](docs/06-merge-policy/README.md) The factory MUST NOT merge its own PR by any path other than the policy script.
- [MG-06](docs/06-merge-policy/README.md) The reason a PR was not auto-merged MUST be visible on the PR or in the job.
- [MG-07](docs/06-merge-policy/README.md) The merge notice MUST be posted to the origin thread.
- [MG-08](docs/06-merge-policy/risk-times-kind.md) Effective required approvals MUST be `max(approvals_for_risk, minimum_for_kind)`.
- [MG-09](docs/06-merge-policy/risk-times-kind.md) Auto-merge MUST be possible only when both the risk rule and the kind rule allow it, and no protected path is touched.
- [MG-10](docs/06-merge-policy/risk-times-kind.md) The policy (approvals per risk, auto-merge risks, minimum per kind, protected paths) MUST live in one versioned policy file, read by the merge script.
- [MG-11](docs/06-merge-policy/human-review-and-hold.md) Human reviewers SHOULD start from the evidence and the acceptance criteria, then read the diff where the evidence is thin.
- [MG-12](docs/06-merge-policy/human-review-and-hold.md) Approval SHOULD be possible from where the request started (for example a one-click approval in the chat thread that links to the PR).
- [MG-13](docs/06-merge-policy/human-review-and-hold.md) Any person with write access MUST be able to put any PR or job on `hold`, and `hold` MUST stop every automated action on it.
- [MG-14](docs/06-merge-policy/human-review-and-hold.md) User-visible changes SHOULD go through internal dogfooding before general release; without it they are never auto-merged.
- [MG-15](docs/06-merge-policy/human-review-and-hold.md) Until lint, gate and verification are mature, people SHOULD review every PR, and the auto-merge list SHOULD start empty.
- [MG-16](docs/06-merge-policy/incidents.md) Incident jobs MUST never auto-merge, whatever their risk.
- [MG-17](docs/06-merge-policy/incidents.md) The incident PR MUST include a regression test reproducing the error and a short root-cause note.
- [MG-18](docs/06-merge-policy/incidents.md) Alerts SHOULD create one job per distinct error (deduplicated by fingerprint), labeled with their source.
- [MG-19](docs/06-merge-policy/incidents.md) An incident job that stays in one state longer than a short configured threshold SHOULD alert an operations channel.
- [MG-20](docs/06-merge-policy/incidents.md) When the error cannot be reproduced, the job MUST go to `hold` and the on-call person MUST be told, rather than receiving a speculative fix.

## 07. Memory and context

- [MC-01](docs/07-memory-and-context/README.md) Every agent run MUST start with a briefing: relevant procedures, learnings and similar past runs for the task and repository.
- [MC-02](docs/07-memory-and-context/README.md) Every run MUST end by recording an outcome and zero to five reusable learnings.
- [MC-03](docs/07-memory-and-context/README.md) Memory MUST be partitioned by scope (agent, project, domain, global), and an agent's identity and scopes MUST come from authentication.
- [MC-04](docs/07-memory-and-context/README.md) Anything retrieved from memory or documents MUST be treated as reference material, never as instructions.
- [MC-05](docs/07-memory-and-context/README.md) The product spec (what the factory should build, with acceptance criteria per module) MUST live in the repository in a form agents read before coding.
- [MC-06](docs/07-memory-and-context/README.md) Learnings that keep recurring SHOULD graduate into code (a check, a skill, a spec update), not grow the memory forever.
- [MC-07](docs/07-memory-and-context/scoped-memory.md) The memory service MUST derive the caller's identity from authentication (service account, token), never from a tool parameter.
- [MC-08](docs/07-memory-and-context/scoped-memory.md) Every read MUST pass through one scope filter function; tests MUST try to read another scope and fail.
- [MC-09](docs/07-memory-and-context/scoped-memory.md) Scopes SHOULD be: `agent` (free writes), `project` (agents of one repository), `domain` (a group of projects), `global` (read-only for agents).
- [MC-10](docs/07-memory-and-context/scoped-memory.md) Writes to shared scopes MUST go through a proposal that a person or a policy promotes.
- [MC-11](docs/07-memory-and-context/scoped-memory.md) Entries MUST carry provenance (run id), confidence and validity, and MUST be invalidatable when proved wrong.
- [MC-12](docs/07-memory-and-context/scoped-memory.md) The service SHOULD be stateless and expose its tools through a standard protocol (for example MCP) so any agent harness can use it.
- [MC-13](docs/07-memory-and-context/briefing-and-reflection.md) The briefing MUST be requested with the task description and repository, before the agent reads code, and MUST be bounded in tokens.
- [MC-14](docs/07-memory-and-context/briefing-and-reflection.md) The briefing SHOULD contain procedures (how things are done here), learnings (facts discovered by earlier runs), and summaries of similar runs with their outcomes.
- [MC-15](docs/07-memory-and-context/briefing-and-reflection.md) The briefing MUST be wrapped and labeled as reference material, so the agent does not follow instructions embedded in it.
- [MC-16](docs/07-memory-and-context/briefing-and-reflection.md) At the end, the run MUST record its outcome (`success`, `partial`, `failure`, `aborted`), a one-paragraph summary, and zero to five learnings of one to three sentences each.
- [MC-17](docs/07-memory-and-context/briefing-and-reflection.md) A learning MUST be reusable by a future run on a different task. Status updates and task-specific details are not learnings.
- [MC-18](docs/07-memory-and-context/agent-readable-specs.md) The product spec MUST live in the repository: a roadmap (order, status, open decisions) and one file per module with problem, expected result, numbered acceptance criteria, out of scope and gaps.
- [MC-19](docs/07-memory-and-context/agent-readable-specs.md) Acceptance criteria MUST be verifiable by a test or an artifact.
- [MC-20](docs/07-memory-and-context/agent-readable-specs.md) Triage MUST map each request to a module; the reviewer MUST check the PR against that module's criteria.
- [MC-21](docs/07-memory-and-context/agent-readable-specs.md) A PR that fulfils or changes a criterion MUST update the module's status and gaps in the same PR.
- [MC-22](docs/07-memory-and-context/agent-readable-specs.md) Architecture decisions MUST be recorded as short ADRs next to the spec.
- [MC-23](docs/07-memory-and-context/agent-readable-specs.md) When a human-facing version of the spec exists elsewhere, the repository version MUST be declared the source of truth for agents.
- [MC-24](docs/07-memory-and-context/agent-readable-specs.md) Diagrams SHOULD be text (Mermaid), so agents can read and update them.

## 08. Self improvement

- [SI-01](docs/08-self-improvement/README.md) The factory's definition (agents, prompts, models, triggers, tools, gate, policy) MUST be code in a repository, changed only through pull requests.
- [SI-02](docs/08-self-improvement/README.md) Every session MUST be recorded: conversation, tool calls, diffs, evidence, cost, duration, outcome.
- [SI-03](docs/08-self-improvement/README.md) A baseline of delivery metrics MUST be measured before the factory starts, and the same metrics MUST be tracked continuously.
- [SI-04](docs/08-self-improvement/README.md) Quality MUST be measured with online evals on recorded sessions and with benchmarks built from the team's own past tasks, not with public benchmarks alone.
- [SI-05](docs/08-self-improvement/README.md) Agents SHOULD aggregate failures into patterns and open pull requests against the factory definition; those PRs MUST be merged by people (protected paths).
- [SI-06](docs/08-self-improvement/README.md) Goal-oriented work ("reduce p99", "keep parity") SHOULD start only after evals and metrics exist for the goal.
- [SI-07](docs/08-self-improvement/record-everything.md) Each run MUST store, linked to its job and run id: the conversation, tool calls and outputs, the diff, evidence artifacts, cost, duration and outcome.
- [SI-08](docs/08-self-improvement/record-everything.md) The record MUST be centralized (one system of record across agents and teams), not scattered across CI logs and laptops.
- [SI-09](docs/08-self-improvement/record-everything.md) Cost and duration MUST be attributed per stage (triage, build, each review round).
- [SI-10](docs/08-self-improvement/record-everything.md) Raw artifacts SHOULD expire on a schedule; summaries and learnings MAY be kept longer.
- [SI-11](docs/08-self-improvement/record-everything.md) Records MUST NOT contain secrets. Redaction MUST happen before storage.
- [SI-12](docs/08-self-improvement/metrics.md) The baseline MUST be taken before the factory starts building for a team.
- [SI-13](docs/08-self-improvement/metrics.md) The metrics below MUST be tracked per week, and SHOULD be split by risk and kind.
- [SI-14](docs/08-self-improvement/metrics.md) Throughput MUST NOT be reported without a quality metric next to it.
- [SI-15](docs/08-self-improvement/metrics.md) Budget limits (daily and monthly cost) MUST exist and MUST stop new dispatches when reached.
- [SI-16](docs/08-self-improvement/evals-and-benchmarks.md) Online evals SHOULD be narrow scorers (LLM-as-judge or deterministic) that each detect one failure type, for example redundant tests, ignored repository skills, unreproduced bug fixes.
- [SI-17](docs/08-self-improvement/evals-and-benchmarks.md) Every session MUST be eligible for scoring; scores MUST be stored with the session.
- [SI-18](docs/08-self-improvement/evals-and-benchmarks.md) A private benchmark MUST be built from real past tasks with known good outcomes.
- [SI-19](docs/08-self-improvement/evals-and-benchmarks.md) Model and harness changes (including routing cheaper models to narrow stages) MUST be justified by a cost × quality comparison on that benchmark.
- [SI-20](docs/08-self-improvement/evals-and-benchmarks.md) Domain agents MUST each have their own eval measuring the business outcome they own.
- [SI-21](docs/08-self-improvement/factory-as-code.md) The factory MUST be declared in files: agents, prompts, models per stage, triggers, tools and MCP servers, execution engine per stage, gate, merge policy, budgets.
- [SI-22](docs/08-self-improvement/factory-as-code.md) These files MUST be protected paths: agents may propose changes, people merge them.
- [SI-23](docs/08-self-improvement/factory-as-code.md) Changes to the factory SHOULD be testable side by side (A/B on a share of jobs or a benchmark replay) before full rollout.
- [SI-24](docs/08-self-improvement/factory-as-code.md) Rollback of a factory change MUST be a revert of one PR.
- [SI-25](docs/08-self-improvement/factory-as-code.md) Moving a stage between execution engines (for example from CI runners to a container service) MUST be a configuration switch, so it can be done stage by stage and reverted.

## 09. Adoption

- [AD-01](docs/09-adoption/README.md) The build order MUST be: guardrails and gate → isolated environments → end-to-end pipeline with human merge → auto-merge for low-risk kinds → self-improvement loop.
- [AD-02](docs/09-adoption/README.md) Autonomy MUST grow one step at a time, per kind and per repository, driven by metrics.
- [AD-03](docs/09-adoption/README.md) The factory SHOULD build itself: once the spine exists, new factory features are requested through the factory, one small module at a time.
- [AD-04](docs/09-adoption/README.md) Buy commodity parts (the coding agent, sandboxes, previews); build only the glue (intake, gate, job state, merge policy, metrics).
- [AD-05](docs/09-adoption/README.md) Engineers MUST own outcomes (a product area, a metric), not a queue of tickets handed to agents.
- [AD-06](docs/09-adoption/build-order.md) Each phase MUST have exit criteria measured against the baseline before the next phase starts.
- [AD-07](docs/09-adoption/build-order.md) Auto-merge MUST NOT be enabled for any kind until the revert and incident rates for that kind, under human merge, are at or below baseline.
- [AD-08](docs/09-adoption/build-order.md) The first two weeks SHOULD produce: baseline metrics, a trimmed instructions file, the single gate, lint rules for the top five recurring corrections, versioned deny rules, the run environment definition, the opt-in label and flow for one team, memory recording for every run.
- [AD-09](docs/09-adoption/trust-ladder.md) A new agent or a new repository MUST start at the read-only rung.
- [AD-10](docs/09-adoption/trust-ladder.md) Moving up a rung MUST be a deliberate, recorded decision based on metrics, not a default that happens with time.
- [AD-11](docs/09-adoption/trust-ladder.md) Each rung MUST be reversible: a person can move an agent or a kind back down at once.
- [AD-12](docs/09-adoption/trust-ladder.md) Agents SHOULD have a visible identity (name, account) and appear where the team works, so people know who did what.
- [AD-13](docs/09-adoption/human-roles.md) Teams SHOULD be small pods (two or three engineers) with vertical ownership of a product area: bug intake, QA, product decisions and their own board.
- [AD-14](docs/09-adoption/human-roles.md) Engineers MUST own outcomes (a metric, a user flow), not the act of passing tickets to agents.
- [AD-15](docs/09-adoption/human-roles.md) Someone MUST own the factory itself ("factory engineering"): guardrails, gate, prompts, evals, cost.
- [AD-16](docs/09-adoption/human-roles.md) People MUST keep the decisions the policy reserves for them: product direction, risk acceptance, protected paths, incident merges, infrastructure applies.
- [AD-17](docs/09-adoption/human-roles.md) Alignment SHOULD use visuals (diagrams, mockups, videos) rather than walls of text.
